## 1. 产品定位

以 Apple Watch 为主要感知入口，以 iPhone 为个人档案和分析中心，构建全面的个人健康与情绪管理助手。在用户分项授权后观察生活变化，连接身体、情绪、精力与情境线索，提供克制的主动帮助，并记录调整效果。

首个用户为开发者本人。首版追求可持续自用、离线可用、数据可解释，不以使用时长、打卡次数或聊天量作为成功目标。休息提醒只是服务之一，不能替代整体身心管理愿景。

### 1.1 五个管理维度

| 维度 | 输入 | 输出 |
| --- | --- | --- |
| 身体状态 | 睡眠、活动、训练、可获得的身体信号、本人症状 | 与个人近期状态的变化比较 |
| 情绪体验 | 用户主动表达、可忽略的确认、事件背景 | 本人感受记录及变化线索 |
| 精力与恢复 | 用户反馈、睡眠、活动负担 | 恢复机会与安排建议 |
| 生活行为 | 作息、运动、用户标注的工作与社交情境 | 行为与身心变化的关联 |
| 个人目标 | 用户想改善的问题、现实约束、尝试结果 | 小规模改善计划和复盘 |

身体、情绪、精力分别展示。不得生成含义不清的统一“健康总分”，也不得从心率等身体信号直接断言用户的情绪或心理诊断。

### 1.2 核心原则

1. 默认在端侧处理和保存数据，基础功能不依赖网络或云账户。
2. 被动观察优先，关键确认少量且可忽略，不要求每日打卡。
3. 明确区分观测事实、本人感受与待验证解释。
4. 共同出现只支持关联，不支持因果结论。
5. 证据不足、数据过期或没有有用动作时保持安静。
6. 权限按用途请求，支持暂停、撤销、导出和删除。
7. 不承诺持续实时采集、准确识别所有情绪或系统后台永久运行。

## 2. 用户场景与范围

### 2.1 核心场景

- 早晨查看最近一次可用睡眠记录，了解数据更新时间和缺失情况。
- 训练或工作后，在手表上用几次点击记录“身体累、情绪愉快、精力一般”等独立感受。
- 晚间在手机查看健康记录与本人标注的时间线，修正系统的解释。
- 连续一段时间观察后，查看“晚睡与第二天精力偏低多次共同出现”等个人模式及反例。
- 发起一个“尝试提前结束晚间训练”的小计划，记录执行情况与主观结果。
- 不打开应用时，在系统允许的机会内收到少量有依据的提示；未送达时仍能在应用中查看。

### 2.2 首版范围

| 优先级 | 内容 | 完成定义 |
| --- | --- | --- |
| P0 | iPhone 本地档案、健康数据读取、睡眠与活动展示 | 可在真机读取至少一种已授权且存在的数据，离线查看 |
| P0 | Watch 快速反馈与可靠同步 | 手机暂不可达时保留反馈，恢复后不重复写入 |
| P0 | 身体、情绪、精力独立记录与时间线 | 可新增、编辑、删除，明确来源 |
| P0 | 规则建议、通知调度与静默降级 | 建议可解释，权限拒绝后不影响查看记录 |
| P0 | 数据控制、导出、恢复、删除 | 通过端到端演练，无需云服务 |
| P1 | 关联观察、反例、改善计划与周回顾 | 每条观察可追溯到本地证据 |
| P2 | 设备支持时的端侧自然语言模型 | 不可用时规则和模板继续工作 |
| 后续 | 云端增强、录音、照片、人物关系、位置和日历 | 独立设计、独立授权，不作为首版前置条件 |

首版可先完成 P0，再进入自用迭代完善 P1；整体设计从一开始保留跨场景关系和长期记忆结构。首版不做人物好坏排行、不推断具体疾病、不提供诊疗建议、不自动监听周围谈话。

## 3. 成功标准

以下是建议的首轮自用验收门槛，非已测得结果：

- 完整断网时，记录、查看、规则分析、计划与本地导出仍可使用。
- 手机与手表断连后重连，测试反馈最终恰好入库一次，删除不被旧队列复活。
- 不授权健康数据或通知时可进入应用，明确显示不可用原因。
- 每条主动建议显示依据、数据时间、可选动作及忽略入口。
- 自用两周，统计通知有用/无用/未反馈，复盘是否过度打扰；未反馈不计为满意。
- 存储占用可查询，清理不会静默丢弃用户确认的记录。
- 不向云端发送个人档案；可选云功能未开启时没有模型 API 调用。
- 完成一次本地备份、清空应用档案、恢复并核对记录数与代表性内容。

## 4. 平台与开发条件

推荐原生 Swift、SwiftUI，iPhone 作为主应用，Watch 作为配套应用。具体最低 iOS/watchOS 版本在确认现有设备与 SDK 后确定，不能在未验证前承诺系统模型或新 API 可用。

开发与签名需要兼容的 Mac、macOS 与 Xcode。iPhone、Apple Watch 配对真机用于 HealthKit、WatchConnectivity、后台和功耗验证。模拟器用于页面与可控数据测试，不代表真实传感器、后台交付或通知可靠性。

第一周验证开发者账号的签名期限、HealthKit 能力及目标设备安装路径。免费账号是否满足当前组合需实际验证；上架、长期分发或特定能力的账号要求按 Apple 当时规则核实。

Linux 云环境可用于文档、代码编辑和适用的独立逻辑检查，不能替代 Xcode、Apple SDK、签名及真机运行。代码仓为空时不需要预装后端、数据库服务或云模型依赖。

## 5. 信息架构与页面

### 5.1 iPhone

| 入口 | 页面内容 | 主要交互 |
| --- | --- | --- |
| 现在 | 最近可信观察、身体/情绪/精力独立摘要、一个可选动作 | 查看依据、记录感受、忽略、纠正 |
| 今天 | 按时间排列的健康数据、本人反馈、计划事件 | 日期切换、来源筛选、补记、编辑 |
| 我的规律 | 关联候选、证据窗口、有效样本、反例、用户修正 | 查看证据、认可/否认、停止提示 |
| 我的改善计划 | 当前小调整、执行记录、回顾 | 创建、暂停、结束、记录结果 |
| 设置与数据 | 权限、静默、空间、模型、导出恢复、删除 | 分项管理、查看本地处理说明 |

空状态必须区分：尚无数据、未请求权限、已请求但没有可读取数据、设备暂不同步、分析样本不足。不得把“读取不到”一律标记为“用户拒绝”；HealthKit 对读取授权的可观测状态受隐私机制限制。

### 5.2 Apple Watch

- 首页：最近同步状态、一个当前可执行动作、快速反馈入口。
- 快速反馈：情绪、身体疲劳、精力可分别选择“未填写”，不强制填全。
- 可选情境：工作、运动、休息、社交、其他；首版不要求输入人物信息。
- 提交后显示“已在手表保存”或“已同步到手机”，不可混淆。
- 支持返回与取消；交互目标为十几秒内完成，真机可用性测试后调整。

## 6. 首次使用与权限

1. 说明本地优先和能力边界，允许直接进入体验。
2. 选择一个当前目标，也可跳过。
3. 用户开启健康观察时，解释每种数据的用途并请求必要读取权限。
4. 用户开启主动提示时再请求通知权限，展示静默时段设置。
5. 检测手表配对和应用可用情况，不可用时手机独立工作。
6. 首次导入展示进度、可取消；明确最近更新时间。

不在首屏一次性索要麦克风、位置、日历、照片等全部权限。首版原则上只读健康数据，不写回 HealthKit；若未来需要写回，单独定义数据类型、授权和去重方案。

## 7. 健康数据接入

### 7.1 首轮数据

优先接入设备实际提供的睡眠、步数、活动/训练记录；静息心率等作为增强项，逐项验证可用性和意义。心率变异性不作为情绪识别真值，不承诺任意时刻都能取得最新样本。

每条数据保存原始来源标识、时间区间、时区信息、单位、导入时间、质量标记和外部标识。原始健康样本保留在 HealthKit；应用尽量保存索引、必要摘要和可重算特征，避免无期限复制完整高频数据。

### 7.2 增量同步

- 手机执行首次有界导入，建议先读取最近 30 天；用户可后续扩展。
- 使用适用的增量查询机制，持久化查询游标；重复批次不能产生重复记录。
- 正确处理源样本删除；相应特征失效并重算，关联证据同步更新。
- 后台更新为机会式，应用回到前台执行补齐。
- 前台页面显示最后成功导入时间，不把旧数据表现为实时状态。

### 7.3 睡眠处理

跨午夜睡眠按会话聚合，保留开始和结束时间；“在床”与“睡着”不可直接相加。多个来源重叠时以明确、稳定的来源优先规则裁剪，不重复累计。夏令时与旅行期间按绝对时间计算时长，按用户查看的本地日期组织页面。

需要覆盖的样例：跨午夜、午睡、重叠来源、无分期、仅在床、样本删除、跨时区、数据晚到。没有足够可用记录时仅展示事实，不计算看似精确的睡眠质量分数。

## 8. 本地数据模型

| 实体 | 关键字段与用途 |
| --- | --- |
| HealthReference | 来源 ID、类型、区间、单位、源版本/删除状态 |
| DailyFeature | 日期/时区、睡眠/活动摘要、覆盖度、算法版本 |
| FeelingRecord | UUID、发生时间、记录时间、独立感受、情境、输入设备、修订号 |
| Observation | 事实/反馈/假设类型、证据 ID、窗口、置信说明、用户修正 |
| Suggestion | 依据、动作、有效期、优先级、发送与反馈状态 |
| Experiment | 目标、具体调整、观察指标、时间范围、执行与结果 |
| SyncEnvelope | 消息 UUID、实体 UUID、操作、版本、确认、删除标记 |
| AppSettings | 授权相关说明、通知偏好、静默时段、保留策略 |

建议使用 SwiftData 或 Core Data 的本地持久化方案，选型以最低系统版本和迁移试验为准。数据访问通过独立仓储层；分析算法不依赖页面生命周期。日志只记录非敏感运行信息，不包含健康记录、聊天内容、密钥或完整导出数据。

## 9. 个人基线与关联分析

### 9.1 基线

第一阶段采用稳健统计与规则，优先中位数、分位数及滚动窗口。建议使用最近 14–28 个有数据日建立个人基线，至少 7 个有效日才展示初步比较；这些是待校准的工程默认值，不是医学阈值。

显示有效天数、缺失比例和窗口。缺失不填为零，异常数值先做数据质量检查。新设备、作息突变和长期中断后标记基线可能失效。

### 9.2 候选模式

可观察的问题包括晚睡与次日精力、训练时间与入睡时间、用户标注的社交与主观愉快、拖晚工作与睡眠缩短。只使用用户同意且实际可获得的数据，不自动推断会议或人物身份。

候选展示包含：条件、结果、时间窗口、有效配对数、反例、缺失说明和可能的其他解释。初步模式建议至少有 5 次有效配对并横跨两周，仍应标注“待验证”，不得因达到门槛便声称存在因果关系。用户否认后保存修正，降低相关提示，不把否认当作错误答案。

### 9.3 长期记忆

保存用户确认的目标、约束、有效/无效方法和带证据的观察。新记录与旧结论冲突时降低旧结论可信度，并展示修订原因；不把模型生成文本直接写成个人事实。

## 10. 主动服务与通知

所有睡眠、运动、工作、社交候选进入同一调度器，避免相互冲突。排序考虑证据新鲜度、用户目标、可行动性、近期同类反馈和打扰成本。

建议初始策略：每天最多 2 条主动建议，同类建议至少间隔 4 小时；默认静默 22:00–08:00，用户可修改。静默期间的过期建议直接丢弃，不在早晨集中补发。主动预算不包括用户主动设置的明确提醒，但仍遵守其静默偏好。

发送前检查权限、静默、预算、有效期、是否已完成动作、数据是否过期及是否已有等价建议。通知不承诺精确送达；系统不调度时，前台补齐分析并在“现在”展示有效建议，不能补发过期通知。

每条建议提供忽略、暂缓和“没帮助”入口。锁屏默认使用中性文案，避免展示具体情绪、症状或人物信息。系统专注模式与平台规则优先，不设计紧急医疗告警。

## 11. 手机与手表同步

使用 WatchConnectivity 的适用通道：即时交互只在会话可达时使用，耐久反馈依赖持久队列与后台传输机制。传输成功回调不等于业务持久化成功，以接收方入库确认关闭待发送状态。

- 每条反馈创建稳定 UUID；双方重复接收均幂等。
- 队列跨应用重启保留；采用有界退避，避免频繁唤醒。
- 编辑与删除带版本和墓碑；旧消息不得覆盖新版本或复活删除记录。
- 冲突采用明确定义的版本比较，无法可靠判断时保留可供用户确认的版本；不只依赖设备时间戳。
- 整体清除产生新的数据代次，拒收旧代次队列；离线手表下次连接执行清除并确认。
- 不把整个健康档案持续复制到手表，只同步展示所需摘要和待确认反馈。

验收覆盖：断连、重复传输、乱序、应用重启、时钟偏差、删除后重连、手机重装。未配对设备的残留数据不能承诺远程立即删除，须向用户说明其本地清除路径。

## 12. AI 分层与解释

### 第一层：规则、统计、模板

必须离线工作。将结构化事实与证据转换为简短观察和一个动作。允许“目前数据不足，暂时无法判断”。无自由对话模型时仍提供有限问题入口，如“最近睡眠有什么变化”。

### 第二层：端侧模型增强

仅在设备、系统、地区、模型已下载且运行时可用时开启。通过能力探测选择实现；不把某个系统模型 API 当作所有设备的前提。限制输入窗口和生成长度，避免长时间占用手表或手机算力。

模型只解释可检索到的证据；输出区分事实、本人反馈和假设。无法引用本地记录的个性化结论应被拒绝或降级为一般说明。模型不可用时恢复模板，不影响数据功能。

### 第三层：可选云端增强

首版不要求实现。未来须由用户单独开启，并在每次发送前展示或明确约定最小信息范围。默认不上传整个档案，不自动回退到云端，不把“不训练模型”等同于“不存储数据”。须核实服务商留存政策后再承诺。密钥使用安全存储，不进入仓库或日志。

## 13. 隐私、存储与恢复

### 13.1 数据边界

默认不启用 CloudKit/iCloud 档案同步、第三方分析 SDK或云模型。iPhone 本地应用数据应使用适当文件保护；密钥放 Keychain。必须明确系统设备备份与应用主动云同步的区别：不能因为应用没有云服务就承诺数据绝不会出现在系统备份中。敏感数据库及备份文件的系统备份策略需实现并验证，向用户展示实际行为。

### 13.2 容量治理

设置页分别展示数据库、缓存、模型与导出占用。建议每日摘要和本人记录长期保留，可重算缓存按保留窗口清理；具体窗口可配置。删除模型不删除档案，清理缓存不删除用户反馈。磁盘不足时优先停止大导入/模型下载，保留已有数据并给出恢复路径。

录音首版不采集。未来启用时应明确开始/停止状态、保留周期和本地转写能力，禁止默认无限期留存音频。

### 13.3 导出、恢复和删除

- 提供带 schema 版本的机器可读导出，包含反馈、计划、摘要、设置与必要来源说明；说明哪些 HealthKit 原始数据不包含在导出中。
- 导出前提示敏感性与目标位置；优先采用成熟的受支持加密容器，不自创密码算法。加密导出未实现前不得声称具备安全备份能力。
- 导入先校验版本、完整性、记录 ID 与容量，预览影响；失败不能破坏现有档案。
- 本地删除可分范围，整体删除需二次确认，取消通知、失效缓存并处理同步队列。
- 删除应用档案不删除 HealthKit 源数据；应用只读场景不应尝试删除其他来源样本。
- 用户已导出文件、系统历史备份和离线设备上的副本不承诺自动清除，需明确管理入口。

## 14. 功耗、性能与故障降级

避免为采样而模拟运动会话、持续定位或高频轮询。分析以增量数据触发，重计算在充电等合适条件下执行；前台只处理页面需要的有限窗口。手表不运行大型模型。

建议首轮工程指标：本地首页在代表性真机上冷启动可交互约 2 秒量级；连续 7 天比较电池、存储及后台行为。记录设备型号、系统版本、测量条件和波动，再确定正式性能门槛。

| 故障 | 用户可见行为 |
| --- | --- |
| 无健康数据 | 展示来源与更新时间说明，允许手动记录 |
| 后台未运行 | 前台补齐，显示滞后，不伪装实时 |
| 手机不可达 | 手表本地保存，展示待同步 |
| 模型不可用 | 模板解释继续工作 |
| 数据库迁移失败 | 保留原数据，停止写入并提供恢复说明 |
| 存储不足 | 停止大任务，不静默删除本人记录 |
| 云请求失败 | 保留本地能力，不扩大上传范围重试 |

## 15. 测试与验收矩阵

| 范围 | 关键测试 | 通过条件 |
| --- | --- | --- |
| 数据逻辑 | 重叠睡眠、跨日/时区、删除、缺失 | 不重复累计，可追溯，缺失不作零 |
| 权限 | 首次拒绝、部分授权、后续撤回 | 无崩溃，无越权，说明与实际能力一致 |
| 同步 | 断连、重复、乱序、重启、墓碑 | 最终一致，不丢反馈，不复活删除 |
| 通知 | 静默、预算、过期、无权限、专注模式 | 应用不安排违规候选，正确降级 |
| 关联 | 样本不足、反例、用户否认、旧证据删除 | 不输出无依据结论，修正可保留 |
| 离线 | 飞行模式下操作所有 P0 页面 | 基础闭环完成，无云调用依赖 |
| 隐私 | 日志、网络、导出、清空、备份策略 | 与产品声明一致，无意外泄露 |
| 恢复 | 导出再导入、损坏文件、旧版本 | 核对记录与内容，失败不破坏数据 |
| 真机 | iPhone/Watch安装、后台和耗电 | 明确设备及系统下的实测结果 |

分析模块使用可控合成样本做单元测试；持久化与同步用集成测试；页面用少量关键流程测试；权限、后台、传感器和耗电必须真机验收。测试报告分别列通过、失败、跳过和未执行，零测试不能算验证。

## 16. 实施计划：每周约 15–20 小时，12–16 周

| 周次 | 交付 | 出口条件 |
| --- | --- | --- |
| 1 | 确认设备、学习 Xcode/Swift 基础、建立 iPhone/Watch 空应用 | 两台真机可安装，签名与能力边界明确 |
| 2 | SwiftUI 页面骨架、本地反馈存储 | 离线新增/编辑/删除，重启保留 |
| 3 | HealthKit 权限和一种真实数据读取 | 读取与空状态可解释，前台刷新成功 |
| 4 | 睡眠/活动增量导入与摘要 | 去重、删除和跨日样例通过 |
| 5 | Watch 反馈与手机同步 | 断连重连和重复传输通过 |
| 6 | “现在/今天”完整页面，基线初版 | 数据时间和证据可追溯 |
| 7 | 规则建议、通知预算与静默 | 过期、拒绝权限、前台补齐通过 |
| 8 | 容量、导出恢复、删除与隐私检查 | 完成一次清空恢复演练，P0 闭环 |
| 9–10 | 关联候选、反例、改善计划 | 能复盘一次小调整，说明证据不足 |
| 11–12 | 持续自用、功耗与可靠性修复 | 两周结果记录，无未解释的数据丢失 |
| 13–16 | 缓冲、可选端侧模型、分发准备 | 先解决 P0 问题，再增加模型能力 |

排期是学习与实现估算，设备、账号、后台限制和个人时间可能延长。模型训练不是第一阶段前置工作；先做好可靠采集、端侧记录、规则闭环和恢复能力。

## 17. 开发任务拆分与完成规则

首批任务建议按顺序创建：

1. DEV-01：记录设备与工具版本，验证签名、HealthKit 和 Watch 真机安装。
2. DEV-02：确定最低系统版本、存储方案及 schema v1，跑通持久化迁移样例。
3. DEV-03：手机独立反馈闭环和核心页面空状态。
4. DEV-04：HealthKit 只读导入、游标、去重、删除和睡眠摘要。
5. DEV-05：手表持久队列、入库确认、版本冲突及清除代次。
6. DEV-06：个人基线、解释模板、证据追溯和用户修正。
7. DEV-07：统一建议调度器、静默、预算、过期和通知降级。
8. DEV-08：导出恢复、容量治理、隐私与离线验收。
9. DEV-09：规律候选、改善计划与周回顾。
10. DEV-10：连续自用记录，按实测结果决定是否引入端侧模型。

每项任务应有具体输入、可观察输出、失败行为和测试记录。涉及平台 API 的实现以当前 Apple 官方文档与目标真机结果为准，不因模拟器成功就标记全部完成。

## 18. 待确认事项与发布门槛

不影响本文落库，但开始原生实现前需要确认：Mac/macOS/Xcode、iPhone/iOS、Watch/watchOS、可投入时间及账号能力。后续根据实机确定最低系统版本、系统模型路径与通知可靠性。

首个自用版本发布门槛：P0 闭环、离线与恢复通过，核心同步无未解释丢失，权限与隐私声明真实，已知限制有记录。P1 关联仍可处于实验状态，不能将未经验证的模式包装成健康结论。
